# Incident Reports — Design

Date: 2026-10-06
Repos: `capstone-backend` (NestJS + TypeORM + Supabase), `lams-web-app` (Angular 20)

## Goal

Let any user file an incident report against an asset (damage, malfunction, loss, etc.), have staff review and resolve it, and give each asset a printable report that includes its incident and maintenance history.

## Decisions

| Topic | Decision |
|---|---|
| Who can file | Any logged-in user (SuperAdmin, CampusAdmin, LabTech, Faculty) |
| Approval | Reports filed by LabTech, CampusAdmin or SuperAdmin start as **Approved**. Reports filed by Faculty start as **Pending**. |
| Lifecycle | `Pending → Approved → Resolved`, or `Pending → Rejected`. No other transitions. |
| Who reviews | LabTech or CampusAdmin of the asset's campus; SuperAdmin for any campus. Covers approve, reject and resolve. |
| Notes | Reject requires a reason. Resolve requires resolution notes. |
| Asset status | Never changed by an incident. Repairs go through the existing maintenance request flow. |
| Form fields | Incident type, severity, incident date, description. No photo/attachments. |
| Enums | Type, severity and status are fixed TypeScript/Postgres enums, not admin-managed lookup tables. |
| Printable report | Client-side PDF (`jspdf` + `jspdf-autotable`): asset details, maintenance history, incident history. |
| Realtime | Not in v1. Pages reload data after each action. |

Enum values:

- `IncidentType`: `Damage`, `Malfunction`, `Lost/Missing`, `Theft`, `Safety Hazard`, `Other`
- `IncidentSeverity`: `Low`, `Medium`, `High`
- `IncidentStatus`: `Pending`, `Approved`, `Resolved`, `Rejected`

## Backend (`capstone-backend`)

New module `src/modules/incidents/`, structured like `src/modules/maintenance/` (entities, dto, enum, controllers, services), registered in the app module.

### Entity / table `incident_reports`

Created by a new TypeORM migration in `src/db/migrations/`.

| Column | Type | Notes |
|---|---|---|
| `incidentId` | varchar(50) PK | Generated by `IdGeneratorService.generateStructuredId` (campus-scoped, module code `IR`) |
| `asset` | FK → `assets.assetId` | required |
| `incidentType` | enum `IncidentType` | required |
| `severity` | enum `IncidentSeverity` | required |
| `incidentDate` | timestamptz | required; cannot be in the future |
| `description` | text | required, non-empty |
| `status` | enum `IncidentStatus` | set on create from reporter role |
| `reportedBy` | FK → `users.userId` | from the authenticated user |
| `reviewedBy` | FK → `users.userId`, nullable | set on approve/reject; on auto-approve equals `reportedBy` |
| `reviewedAt` | timestamptz, nullable | |
| `rejectionReason` | text, nullable | |
| `resolvedBy` | FK → `users.userId`, nullable | |
| `resolvedAt` | timestamptz, nullable | |
| `resolutionNotes` | text, nullable | |
| `createdAt` | timestamptz | `CreateDateColumn` |

### Endpoints — `/api/incident-reports`

All require JWT auth.

| Method & path | Roles | Behavior |
|---|---|---|
| `POST /` | all | Validate DTO; asset must exist and (non-SuperAdmin) belong to the user's campus. Status = `Approved` (with `reviewedBy`/`reviewedAt` = reporter/now) for LabTech/CampusAdmin/SuperAdmin, else `Pending`. |
| `GET /` | all | Optional `status`, `assetId` query params. Non-SuperAdmin users see only their campus. Ordered by `createdAt` DESC. Relations: asset, reportedBy, reviewedBy, resolvedBy. |
| `GET /asset/:assetId` | all | Incident history for one asset, same campus rule, `incidentDate` DESC. |
| `POST /:id/approve` | LabTech, CampusAdmin, SuperAdmin | Only from `Pending`. Sets `Approved`, `reviewedBy`, `reviewedAt`. |
| `POST /:id/reject` | LabTech, CampusAdmin, SuperAdmin | Body `{ reason }` required. Only from `Pending`. Sets `Rejected`, `rejectionReason`, `reviewedBy`, `reviewedAt`. |
| `POST /:id/resolve` | LabTech, CampusAdmin, SuperAdmin | Body `{ resolutionNotes }` required. Only from `Approved`. Sets `Resolved`, `resolvedBy`, `resolvedAt`, `resolutionNotes`. |

Errors:
- Unknown or out-of-campus report/asset → `404 NotFoundException`.
- Invalid transition (e.g. resolve a `Pending` report) → `400 BadRequestException` with a message naming the current status.
- Role violations → existing `@Roles` guard (`403 Required roles: ...`).

Each create/approve/reject/resolve is logged through `ActivitiesService` (new `EntityType` value for incident reports if the enum requires it).

### Tests

Jest spec for the incidents service covering:
- create: status is `Approved` for LabTech/CampusAdmin/SuperAdmin and `Pending` for Faculty;
- create: rejects an asset from another campus;
- approve/reject only from `Pending`; resolve only from `Approved`;
- reject without reason / resolve without notes is rejected by DTO validation;
- review actions on another campus's report return 404 for non-SuperAdmin.

## Frontend (`lams-web-app`)

### Service

`src/app/pages/service/incident-report.service.ts` — `IncidentReport`, `IncidentType`, `IncidentSeverity`, `IncidentStatus` types and HTTP methods: `create`, `getAll(params?)`, `getByAsset(assetId)`, `approve(id)`, `reject(id, reason)`, `resolve(id, resolutionNotes)`. Same style as `maintenance.service.ts`.

### Assets page (`src/app/pages/assets/assets.ts`)

- New row button `pi pi-exclamation-triangle` ("Report Incident") next to Request Maintenance. Visible to all roles; hidden when the asset's status is `Retired`.
- New standalone `ReportIncidentDialogComponent` in `src/app/pages/assets/components/`: Type and Severity selects, date picker (default today, max today), Description textarea; all required. On success shows "Incident recorded" (auto-approved roles) or "Incident submitted for approval" (Faculty). Inputs: `asset`, `visible`; outputs: `visibleChange`, `submitted`.
- View dialog: add an "Incident History (n)" accordion below Maintenance History, same styling. Each entry: type, severity, status pill, incident date, reporter, description, and resolution notes / rejection reason when present. Data from `getByAsset`, loaded in the existing `forkJoin` with `catchError(() => of([]))`.
- View dialog: add a "Print Report" button that calls the new PDF service.

### PDF

`src/app/pages/service/asset-report-pdf.service.ts` — `generate(asset, maintenanceHistory, incidents)` builds one PDF with `jspdf` + `jspdf-autotable`: header with asset name/ID and generation date, asset details table, maintenance history table, incident history table. Empty sections print "No records". File name `asset-report-<assetId>.pdf`. Follows the layout conventions of `masterplan-pdf.service.ts`.

### Incident Reports page

`src/app/pages/incidentreports/incident-reports.component.ts`, routed as `/app/pages/incidentreports` in `pages.routes.ts`, and added to every role's menu in `app.menu.ts` (icon `pi pi-exclamation-triangle`).

- Tabs: All, Pending, Approved, Resolved, Rejected; search box; CSV export of the active tab — same structure as `requestmaintenance.component.ts`.
- Columns: ID, Asset, Type, Severity, Incident Date, Reported By, Status, Actions.
- Status pill colors reuse existing classes: Pending `tag-pending` (orange), Approved `tag-info` (blue), Resolved `tag-success` (green), Rejected `tag-danger` (red). Severity pills: High red, Medium yellow, Low green.
- Actions (LabTech, CampusAdmin, SuperAdmin only): Pending → Approve / Reject (SweetAlert prompt for reason); Approved → Resolve (SweetAlert prompt for notes). View action for everyone shows full details. Faculty see the page read-only.
- Extends `BaseComponent` (`takeUntil(destroy$)`); errors via `ErrorHandlerService.handleHttpError`. Reloads the list after each action.

### Verification

- `npx tsc -p tsconfig.app.json --noEmit` and `npm run build` pass.
- Manual run with both servers: Faculty files → Pending appears on the page → LabTech approves → resolves; LabTech files → appears directly as Approved; asset View shows the history; Print Report downloads a PDF with all three sections.

## Out of scope (v1)

Photo/file attachments, websocket live updates and menu badge counts, editing or deleting reports, automatic asset status changes, automatic maintenance request creation, dashboard widgets.
